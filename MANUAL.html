BrollyZapper — the settings, and what each one is for

Every control an operator can reach, one collapsible section each. OPERATING.md is the full reference — backups, credential rotation, running outside Umbrel; this page is the settings part of it, in a form you can keep open in a tab.

The Settings page

Stored in the database. Everything here takes effect within about two seconds — no restart, no reconnect.

Public domain — where your lightning address lives

The host your lightning address lives on, entered bare: zap.example.com. A pasted https:// is stripped and the scheme remembered beside it, so the page shows which one wallets will be handed. Changing the host on its own returns to https.

Default
Empty. Nostr Wallet Connect works without a domain; a lightning address does not.
If you get it wrong
The app advertises a callback nobody can reach — or worse, one that reaches a different LNURL server that resolves and responds. The Security page's reachability check exists for exactly that: it fetches your own address over the public internet and verifies the response carries this instance's own nostr pubkey and a per-boot header only it emits. A domain pointing somewhere else fails it. Fix that before anything else.
Address name — the part before the @

test gives test@zap.example.com.

Default
Empty.
If you get it wrong
Requests for the old name return a plain 404 with no hint that another name exists — deliberate, so a stranger cannot enumerate what you host.
Trusted proxies — who may claim a client's real IP

A CIDR list of upstream addresses that may be believed when they claim a client's real IP. Empty trusts nothing, which is the safe default: without it, every request behind a proxy arrives as the proxy's own address.

Default
Empty. The deployment's TRUSTED_PROXIES variable is used when this is unset — the setting wins when you set one.
If you get it wrong
Too trusting — a range you do not control — and anyone reaching the app through it can claim any client IP, which makes the per-sender rate limits meaningless. Too strict and every anonymous request shares one bucket, so one busy zapper exhausts the limit for everyone. On Umbrel the package handles this; off Umbrel, see OPERATING.md §Running outside Umbrel.
Relays — where zap receipts are published

One per line. Empty means the built-in default set. Receipts also go to whatever relays each zap request names, so this is an addition to those, not a replacement.

Default
Empty — the built-in set.
If you get it wrong
Unreachable or private-address relays mean receipts reach fewer places than you think. The relays a zap request names are filtered too: private addresses, non-websocket schemes, duplicates and anything past the cap are dropped. Turn the log level to debug and the parse logs what it dropped and why.
Public rate limit — per minute and per hour

The ceiling on total anonymous traffic to the public callback. It governs the public routes only.

Defaults
60 a minute, 600 an hour. This is a backstop on the whole box, not a per-sender limit — that one is separate, fixed at 10/min and 100/hour per verified sender, and deliberately not adjustable.
If you get it wrong
Too low and legitimate zaps bounce during a burst; too high and you widen what a stranger can make your node do. It does not affect the admin login limit — a constant 30 a minute, deliberately not a setting: an operator has no legitimate reason to raise their own brute-force ceiling.
Publishing through Cloudflare? This is the inner of three layers. The edge rate-limit rule is required, not optional — README §Rate limiting at the edge.
Fee reserve — ppm and floor

How much of a payment's value is held back to cover routing fees, as parts-per-million with a floor in msat. The larger of the two applies.

Defaults
10,000 ppm (1%) and 10,000 msat (10 sat).
If you get it wrong
Too low and payments fail to route, or the reserve does not cover the actual fee. Too high and each payment reserves more of the ceiling than it needs, so fewer payments fit in the window.
Log level — debug, info, warn, error

Applied without a restart.

Default
info.
Precedence
This setting overrides the LOG_LEVEL environment variable — the stored value is applied after the environment on boot, so when the two disagree, this one wins. Editing the compose file while a setting is present changes nothing.
When to use debug
Diagnosing delivery: the relay filter and the double-encoding rescue both log there. Safe to leave on briefly, noisy to leave on forever; nothing secret is logged at any level.
Incoming payments raise the spending ceiling — a checkbox with money behind it

When on, sats you receive increase the amount the app may spend.

Default
On — the wallet you zap out of is the wallet zaps land in.
If you turn it off
The ceiling only moves when you move it, so received zaps accumulate without becoming spendable by the app.
This has a real financial consequence in both directions. The conservative reading: "on" means money arriving quietly raises what a compromised app could spend — still bounded by the guard's own caps, which this cannot touch.
Nostr identity — the app's key, not yours

This is the app's own key. It is minted on first run and you do not normally touch it. It signs zap receipts and is announced as nostrPubkey in the lightning address response, so senders' clients recognise receipts as genuinely from this address. You are identified as the recipient by the zap request's p tag — a different thing entirely.

The import field exists for continuity: restoring a backup that lost the database, moving to a new box, or rebuilding an install whose address is already published. Import the key that install used, and previously published receipts stay verifiable. Replacing the key means receipts already published stay signed by the old one.

Do not paste a personal nostr identity key here. It would put a key that can post, DM and delete as you into the part of the app that faces the network — and gain you nothing, because a receipt-signing key is worthless to an attacker and being "you" is not what a zap receipt claims.
Admin password — when the deployment does not manage it

Changeable in the app only when the deployment has not set one. On Umbrel the password is derived per-install and managed by umbrelOS, so the field is absent; off Umbrel, set ADMIN_PASSWORD (minimum 8 characters) or change it here.

Changing it bumps a session counter that is part of every cookie's signature, so every existing session is invalidated — including a copy taken from a browser no longer under your control. That is the point: restarting the app alone would not do it.

The Sending page

Sending is off on a fresh install, and turning it on is deliberately not one click.

The latch — your gate on sending, behind a code

Turning sending on asks the guard for an authorisation: the guard writes a single-use code into a file only you can read, states in its own words what is being authorised, and you type the code back. The app that asked cannot read that file — which is what makes the confirmation mean something: the part of the app facing the network cannot forge it.

The page tells you where the file is and how long the code has left. Codes are single-use and expire; asking again gives you a new one. Turning sending off takes one click and no code.

The two caps — enforced by your node, not by the app

The guard's limits, enforced inside your node's request path rather than in the app:

CapDefaultWhat it bounds
24-hour limit100,000 satsEverything spent in any rolling 24 hours
Per-payment limit25,000 satsOne payment

Lowering either takes one click. Raising one needs a confirmation code. That asymmetry is the whole design: a compromised app can only ever tighten its own limits.

A cap of zero refuses every payment. It does not mean "no cap". And the per-payment limit must stay at or below the 24-hour one, or the guard refuses the change — a per-payment limit above the window could never be reached.

Deployment settings — no page shows these

Environment variables, fixed when the container is created. Nothing in the app can change them, and changing one needs a restart that recreates the container.

The variables — and what going wrong looks like
VariableDefaultWhat it does
GUARD_ALLOW_SENDINGtrue The deployment's ceiling on sending. false is a hard never that nothing inside the app can lift — the Sending page will say so rather than offer a control that cannot work. Not the same as the latch: both must be on.
GUARD_MAX_SPEND_MSAT100000000 The 24-hour cap's starting value. Zero refuses everything.
GUARD_MAX_PAYMENT_MSAT25000000 The per-payment cap's starting value. Must be at or below the 24-hour cap.
GUARD_AUTHORISATION_LOCATIONempty A sentence telling your operator where to find the authorisation file, shown on the Sending page. Free text, deliberately unvalidated. Empty means the page simply says less.
LND_ADDRESS—Your node's gRPC address.
LND_CERT_FILE, LND_ADMIN_MACAROON— Paths to the two files mounted from the node — individual files, never the directory (OPERATING.md §The single-file mount hazard).
CREDENTIALS_DIR, DATA_DIR— The credential volume and the app's own data.
GUARD_SOCKETinside CREDENTIALS_DIR Where the guard listens.
LISTEN_ADDR0.0.0.0:8080 The admin and public HTTP listener.
TRUSTED_PROXIESempty Fallback for the setting of the same name. The stored setting wins when set.
LOG_LEVELinfo Fallback for the stored log level, which wins when set.
ADMIN_PASSWORDempty Minimum 8 characters. Set means the deployment manages it and the in-app change form disappears.
SESSION_SECRETempty Minimum 16 characters. Empty means one is generated and persisted, which is what an off-Umbrel deployment wants.

When a change takes effect

Three categories — the third one surprises people

1. Settings in the app: within about two seconds. Database rows read through a short-lived cache. No restart, no reconnect.

2. The sending latch and the caps: immediately, on the next payment the guard sees.

3. Environment variables: only when the container is RECREATED. A container's environment is fixed at creation. On umbrelOS that means restarting the app from the dashboard (which recreates); docker restart does not, and will leave you editing a compose file wondering why nothing changed.

The precedence trap, stated twice on purpose: for LOG_LEVEL and TRUSTED_PROXIES, the stored setting wins over the environment variable. Changing the compose file while a setting is present changes nothing.
